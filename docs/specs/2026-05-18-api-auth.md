# API authentication (register / login / role-gated routes)

- **Date**: 2026-05-18
- **Status**: Approved
- **Linked issue**: #3
- **Linked PR**: #3

## 1. Context

The application has two audiences:

- **Regular users** create accounts to view their transactions and wallet.
- **Admins** upload spreadsheets and view a global report.

There is no current authentication system. We need a stateless mechanism so
that the API can identify and authorise requests without holding session
state, and a role separation between admins and regular users. The first
admin is created by a database seeder; regular users self-register.

This is also the first PR that exercises the architecture decided in
[ADR-003](../adr/ADR-003-hexagonal-lite.md) and the LGPD protections from
[ADR-002](../adr/ADR-002-lgpd-data-protection.md). Subsequent PRs depend on
the `users` table and the auth middlewares delivered here.

## 2. Requirements

### Functional

- [ ] `POST /api/auth/register` — `{ name, email, cpf, password, consent: true }`
  → `201 { user, token, expiresIn }`. Creates a user with `role='user'`.
- [ ] `POST /api/auth/login` — `{ email, password }` → `200 { user, token,
  expiresIn }`. Works for both admins and users.
- [ ] `GET /api/me` — returns the authenticated user's profile.
- [ ] `authMiddleware` — rejects missing/invalid/expired JWT with 401.
- [ ] `roleMiddleware('admin')` — rejects non-admin tokens with 403.
- [ ] Database seeder creates one admin from env vars on first boot.

### Non-functional

- [ ] **Security**: bcrypt cost 12 for passwords. AES-256-GCM for CPF at rest
  with a per-row IV; HMAC-SHA256 of the CPF as the unique lookup index.
  Helmet + CORS + rate limit (5 req/min on `/auth/*`, 100 req/min global).
  Pino `redact` for `password`, `cpf`, `authorization`.
- [ ] **LGPD**: `consent` must be `true` at registration; persisted in
  `users.consent_at`.
- [ ] **Validation**: every input goes through Zod. CPF validated with the
  Brazilian check-digit algorithm.
- [ ] **Errors**: typed `AppError` family translated to HTTP by a single
  middleware. Never leak stack traces in production responses.

### Data flow — registration

1. Express receives `POST /api/auth/register`.
2. `rateLimit('auth')` middleware (5 req/min/ip).
3. Zod schema validates payload. Bad input → `400 ValidationError`.
4. `AuthController.register` calls `RegisterUser.execute(input)`.
5. Use case:
   - normalise CPF to digits-only,
   - validate check digit,
   - `hash = passwordHasher.hash(password)`,
   - `cipher = cpfCipher.encrypt(cpf)`,
   - `index = cpfIndex.compute(cpf)`,
   - reject if `userRepo.findByEmail(email)` or
     `userRepo.findByCpfHash(index)` returns a row,
   - `user = userRepo.create({ ...input, passwordHash, cpfEncrypted,
     cpfHash, role:'user', consentAt: clock.now() })`,
   - `token = tokenSigner.sign({ sub: user.id, role: user.role })`,
   - return `{ user, token, expiresIn }`.
6. Controller maps to `201` with `Location: /api/me`.

### Data flow — login

1. `POST /api/auth/login` → `rateLimit('auth')` → Zod.
2. `AuthenticateUser.execute({ email, password })`:
   - `user = userRepo.findByEmail(email)` (includes `password_hash`,
     `cpf_encrypted` excluded).
   - If absent or `passwordHasher.verify(password, hash)` is false →
     `UnauthorizedError('invalid credentials')` (single message, no enumeration).
   - `token = tokenSigner.sign({ sub: user.id, role })`.
3. Controller returns `200 { user, token, expiresIn }`.

### Errors

```
AppError (abstract)         status   code
├── ValidationError         400      validation_failed
├── UnauthorizedError       401      unauthorized
├── ForbiddenError          403      forbidden
├── NotFoundError           404      not_found
└── ConflictError           409      conflict
```

`errorHandler` middleware: takes any thrown error, maps `AppError` → its
status + code; otherwise → 500 with code `internal_error` and no body
details.

## 4. Trade-offs / alternatives considered

- **Argon2 over bcrypt**: better resistance to GPU attacks, but bcryptjs is
  more portable on Mac/Win without native compiles, and cost-12 bcrypt is
  acceptable for the test.
- **Refresh tokens**: deferred. Increases code surface and the test focuses on
  the integration story.
- **Per-route Zod inside controller vs. middleware**: kept inline in the
  controller for clarity; controller is the only consumer.

## 5. Test plan

### Unit (Vitest, no DB)

- `shared/cpf` — accepts known valid CPFs, rejects sequences (`111.111.111-11`),
  rejects strings with wrong check digit, normalises punctuation.
- `infrastructure/crypto/AesGcmCipher` — round trip, IV per call, tampering
  detected (auth tag), wrong key → throws.
- `infrastructure/crypto/HmacIndex` — deterministic for the same input,
  different for different input, hex output length 64.
- `infrastructure/crypto/BcryptHasher` — `hash(p)` ≠ `p`; `verify(p, h)` true;
  `verify('wrong', h)` false.
- `infrastructure/crypto/JwtSigner` — sign/verify happy path; expired token
  rejected; tampered token rejected.
- `application/auth/RegisterUser` — persists with hashed password and
  encrypted CPF; rejects duplicates (email + CPF); requires consent.
- `application/auth/AuthenticateUser` — happy path returns token + user;
  wrong password → Unauthorized; unknown email → Unauthorized; soft-deleted
  user → Unauthorized.

### Integration (Vitest)

- Build the Express app with `InMemoryUserRepository` and real middlewares,
  hit it through supertest:
  - `POST /api/auth/register` happy + 400 (missing field) + 409 (duplicate).
  - `POST /api/auth/login` happy + 401 (wrong creds) + 429 (rate limit).
  - `GET /api/me` happy + 401 (no token) + 401 (expired).

### E2E (Vitest + real MySQL via docker-compose; skipped in unit run)

- Run migrations against `nex_test`, seed admin, register a user, login as
  both, hit `/me`. Asserts schema and indices exist.

## 6. Roll-out

- Migration `<ts>-create-users.cjs` adds the `users` table with all columns
  and indices listed in [ADR-002](../adr/ADR-002-lgpd-data-protection.md).
- Seeder `<ts>-admin.cjs` reads `ADMIN_*` env vars; idempotent on
  `email = ADMIN_EMAIL`.
- No backward compatibility concerns — this is the first migration.
